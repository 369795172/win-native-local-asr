### 2026-09-17 — six-step first-run installer (Task 10)

- `feat(setup): six-step installer with mirrors and resume`: `src/WinLocalASR.Core/Setup/SetupRunner.cs` ports the macOS SetupRunner philosophy (one click, self-contained, progress callbacks) onto Windows artifacts — pinned llama.cpp binaries + GGUF instead of a Python venv. Six steps: (1) create `%LOCALAPPDATA%\WinLocalASR\{bin,models}`; (2) download the pinned llama.cpp zip into `bin/` (GitHub direct fails → exactly ONE retry with the ghproxy.cn prefix form `{ghProxyPrefix}{original-url}`); (3) download the Q8_0 GGUF pair into `models/` (huggingface.co fails → hf-mirror.com host swap, per-file); (4) SHA256-verify every artifact against the manifest, THEN extract the whole zip (never extract unverified bytes — the CPU dispatch DLLs are load-time selected); (5) write the installed `versions.json` (raw manifest JSON + the three resolved-path keys `llamaServerPath`/`mainModelPath`/`mmprojModelPath`, atomically) and set `Configured=true` via SettingsStore; (6) invoke the injectable completion delegate (the shell wires `AppController.InitializeAsync`).
- **Resume**: downloads go to `.part` and continue via HTTP Range (`Range: bytes=N-`, 206 + Content-Range); a complete-but-unmoved `.part` finalizes without a request, a `.part` larger than the pinned size restarts cleanly, and a server ignoring Range (200) restarts from scratch. Zip totals come from Content-Range (the llama pin has no sizeBytes; model totals from `sizeBytes`). Cancellation deletes `*.part` recursively but keeps finished artifacts; non-cancel failures KEEP `.part` so the next run resumes (2.5 GB over flaky links WILL interrupt).
- **Idempotence**: the release zip is retained in `bin/` as the step-2 anchor; an existing artifact (zip/model) whose size+SHA match the manifest is skipped with zero server hits, and extraction is skipped when the zip was skipped and `llama-server.exe` exists. Every URL attempted lands in `AttemptedUrls` AND the step log (mirror-switch lines carry the full URL) so a real-machine run can prove whether failover fired.
- **Seams**: everything injectable — install base dir (temp dirs in tests, never real `%LOCALAPPDATA%`), `HttpMessageHandler` (in-process stub file server), `SettingsStore` (temp `%APPDATA%`), failover delay (`MirrorRetryDelay` + injectable `Delay`), completion delegate. HttpClient timeout is infinite (a 2.5 GB download must not die at the 100 s default); transport errors still surface fast and drive failover, true hangs are covered by user cancel + resume.
- `SetupDialog.cs` (App) is a thin WinForms shell over `SetupDialogPresenter` (Core, no WinForms): step bar + per-file bar + step log + Cancel; presenter owns the CTS and marshals progress ticks (file bar only) vs log lines to `ISetupDialogView`; failure keeps the dialog open, success closes it. TOFU policy honored: a null llama.cpp sha256 is frozen into the installed copy after first download.
- Test inventory (13 new in `Tests/Setup/`): QA+ fresh-machine simulation over a real HttpListener file server (fake zip with exe+11 DLL shapes, 100 KB/50 KB fake models) — dirs, whole-zip extraction, byte-exact models, installed manifest loadable through BOTH `VersionManifest.Load` and `LlamaServerPaths.Load` with the exact resolved paths, Configured=true, completion invoked, AttemptedUrls == 3 primaries, all six steps + percent ticks observed; idempotent second run (server hit count unchanged, 3 skip lines, extraction skipped); resume tests — pre-seeded 40 KB `.part` → Range `bytes=40000-` recorded, 206 served, byte-exact assembly (model) and Content-Range-total resume (zip); QA- — wrong model SHA aborts at step 4 ("verification failed", no installed manifest, Configured false, no extraction), llama 404 → exact ghproxy-prefixed URL asserted verbatim (order primary→mirror, mirror-served zip still extracts), mirror-also-404 → SetupException after EXACTLY 2 attempts, model 404 → exact hf-mirror host-swap URL + byte-exact file; cancellation mid-download (blocking stream) → `.part` cleaned, finished zip kept, nothing finalized; URL builders unit-tested against the real repo-root manifest (exact pinned forms). Presenter: progress/log/result forwarding with marshaling, cancel → closed view without success, SetupException message surfaced.
- Local macOS: `dotnet test` → 154 passed / 3 skipped (Windows-only) / 0 failed; 3 consecutive green runs. CI windows-latest: **156 passed / 1 skipped / 0 failed** — https://github.com/369795172/win-native-local-asr/actions/runs/35182582470 (all Setup tests + Windows-only audio/clipboard smokes ran for real).
- Windows gotcha (cost one red CI, fixed in `eecb6f4`): `File.Move` on a `.part` whose `FileStream` was still open — `await using var` disposes at METHOD scope, i.e. after the move. Unix happily moves open files; Windows throws a sharing violation, which the failover layer then misread as "primary failed" and burned the one mirror retry. Fix: scope the write stream in an explicit `await using { … }` block so the handle closes before the move. Same rule applies to the cancel path by construction (the using block unwinds before the OCE handler deletes `.part`).

## Lessons learned

- .NET 10 `dotnet new sln` defaults to the new `.slnx` XML format. Pass `--format sln` when the classic solution file is required (CI paths, older tooling, editor support).
- xunit types are not covered by `ImplicitUsings`; test files need an explicit `using Xunit;`.
- Referencing the NAudio metapackage from a project that multi-targets `net10.0-windows` requires `<EnableWindowsTargeting>true</EnableWindowsTargeting>` on non-Windows hosts: `NAudio.Winsows` carries a `Microsoft.WindowsDesktop.App.WindowsForms` FrameworkReference that cross-platform builds cannot resolve otherwise (NETSDK1073).
